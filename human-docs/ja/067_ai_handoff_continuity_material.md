# AIに作業を引き継ぐとは何か 説明資料

この資料は、人間の異動や退職で技術者がいなくなっても、残されたサービスを維持管理し続けなければならない管理者向けに、
`AIに作業を引き継ぐ` とは何を意味するのかを説明するための原稿である。

ここでいう引き継ぎは、人間の責任を AI へ丸投げすることではない。
構成情報、運用手順、判断理由、障害対応知識を AI が読める形で残し、
新任者が AI を入口にして維持管理へ入れる状態を作ることを指す。

## ゴール

- 技術者がいなくなっても、サービスは残り続けるという管理上の危機感を共有する。
- ソースコードや動作中サービスだけでは、維持管理できないことを理解してもらう。
- 従来のドキュメント残しだけでは足りず、AI を作業 IF にする必要があると理解してもらう。
- AI に渡すべき保守パッケージの内容を具体的に理解してもらう。
- `AI導入とは、既存サービスを人がいなくなっても管理可能な状態に変える継続性対策である` と判断できる状態にする。

## 対象者

- サービスを止められない立場の管理者
- 担当者交代や退職後の保守不能化を懸念している人
- 新任者に既存サービスを引き継がなければならない責任者

## 中心メッセージ

技術者がいなくなっても、サービスは残る。
しかし、理解している人はいなくなる。

問題は、今そのサービスが動いているかではない。
次の変更、次の障害、次の担当者交代に耐えられるかである。

そのためには、ソースコードと動作中サービスだけを残すのではなく、
構成情報、運用手順、判断理由、障害対応知識を AI が読める形で残し、
AI を新任者の作業入口として使える状態にする必要がある。

## 1. 問題提起

- システムは止められない。
- しかし、理解している技術者はいなくなる。
- サービスは事業上残り続けるが、運用文脈は担当者と一緒に失われやすい。

ここで作るべき危機感は、
`サービスは残るのに、理解している人はいなくなる`
という非対称性である。

## 2. 残るものと失われるもの

### 残るもの

- ソースコード
- 本番環境
- DB
- 設定ファイル
- リリース済みサービス

### 失われるもの

- なぜこの設計なのか
- どこを触ると危険なのか
- 障害時に何を見るのか
- リリース時に何を確認するのか
- 過去に何で失敗したのか
- 業務上の例外条件

つまり、技術的な実体は残るが、
運用と判断に必要な文脈は失われやすい。

## 3. 管理上のリスク

文脈がないサービスは、動いていても管理できない。

問題は `今動いているか` ではない。
問題は、次の変更、次の障害、次の担当者交代に耐えられるかである。

管理者向けには、次の言い方が核になる。

- 動いているサービスは資産である。
- しかし、維持管理できないサービスは負債になる。

## 4. 従来の対策の限界

従来は、設計書、手順書、引き継ぎメモを残す。
しかし、それだけでは新任者が状況に応じて使いこなせない。

理由は単純で、ドキュメントは `読むもの` だからである。

必要なのは、状況に応じて:

- 確認する
- 説明する
- 整理する
- 判断を補助する

という入口である。

## 5. AIを使う意味

AI を、残されたサービスを読むための作業 IF にする。

ここでいう `作業 IF` とは、
人が自然言語で依頼し、AI が裏側の情報をたどりながら、
説明、整理、確認、問題解決補助を行う入口を指す。

たとえば新任者は、AI に次のように聞ける。

- このサービスの構成を説明して
- 本番障害時に最初に見る場所を教えて
- この画面を直す場合の影響範囲を出して
- Azure App Service と Azure SQL の関係を整理して
- リリース手順を確認して
- このエラーが出た場合の確認順を出して

Git、Azure、.NET Framework、DB、CI/CD を全部深く知らなくても、
AI を入口にして維持管理へ入れる。

ここが価値である。

## 6. 必要なのは「AIに渡す保守パッケージ」

技術者がいなくなる前に、最低限これを残すべきである。

| 分類 | 残すもの |
|------|------|
| サービス概要 | 何をするサービスか、誰が使うか、業務上の重要度 |
| 構成情報 | Azure App Service、Azure SQL、Storage、外部 API、認証、ネットワーク |
| ソース情報 | リポジトリ、主要プロジェクト、重要フォルダ、ビルド方法 |
| DB情報 | 主要テーブル、マスタ、バッチ、参照関係 |
| リリース手順 | ビルド、デプロイ、設定変更、ロールバック |
| 障害対応 | ログの場所、監視、よくある障害、初動手順 |
| 判断理由 | なぜその構成なのか、触ってはいけない箇所 |
| 未解決事項 | 技術的負債、既知の不具合、今後の改善候補 |

これは `ドキュメント整備` ではなく、
AI が読んで新任者を支援できる保守基盤の整備である。

## 7. 引き継ぎ情報をまとめると何が解けるか

- 背景を AI が要約して説明できる
- 相手が初心者なら概要から、経験者なら判断点中心から説明できる
- ソース、配置情報、構成情報をもとに、何を確認すべきか、どう直すべきかを提示できる
- 新任者が Git やクラウド構成を全部覚える前に、維持管理へ入れる
- 引き継ぎ情報が断片メモではなく、継続利用できる保守文脈へ変わる

## 管理者向けの結論

技術者がいなくなる現場では、
ソースコードと動作中サービスだけを残しても維持管理できない。

構成情報、運用手順、判断理由、障害対応知識を AI が読める形で残し、
AI を新任者の作業入口にする必要がある。

さらに一文で締めるなら、次である。

`AI導入とは、既存サービスを人がいなくなっても管理可能な状態に変えるための継続性対策です。`
