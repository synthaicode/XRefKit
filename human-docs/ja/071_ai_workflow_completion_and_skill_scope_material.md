# AIの作業を途中で終わらせないための仕組み

この資料は、XRefKit における Skill と workflow protocol を、AI を業務で
使う組織の説明用に整理したものである。

ここでいう実行基盤は、旧称の `fm` ではなく、現在の `xrefkit skill`
コマンド群である。`xrefkit skill` は、Skill の業務手順そのものを判断する
AI ではない。Skill 実行を記録、検証、引き継ぎ、完了判定するための
workflow protocol を実行する。

## 伝えたい結論

AI を業務に使うときの問題は、AI が文章やコードを生成できるかだけではない。
依頼された仕事が最後まで行われたか、途中で止まった作業を誰がどこから再開するか、
未解決の判断を誰に渡すかを管理しなければならない。

XRefKit は、この問題を二つに分けて扱う。

- **Skill** は、AI に任せる仕事の責務、判断方法、入出力、境界を定義する。
- **workflow protocol** は、その仕事を完了扱いにしてよい条件を、AI の自己申告ではなく記録と決定論的な検査で管理する。

この分担により、AI は広すぎる仕事を一度に抱えず、限定された責務に集中できる。
一方で、途中終了、未確認の出力、未解決の不確実性、引き継ぎ漏れを、
「完了」として見逃しにくくする。

## 何が問題になるのか

AI を使った作業は、次の理由で途中終了しやすい。

- セッション、実行時間、利用上限、担当者の交代によって実行が中断する。
- AI が一部の成果を出した時点で、依頼全体が終わったように見える。
- 調査、実装、確認、根拠の記録、次工程への引き渡しが、一つの応答に混ざる。
- 例外や判断保留が、本文の末尾や会話履歴に埋もれる。

通常の会話だけでは、AI が何を完了したか、何を確認していないか、何を次の人へ
渡すべきかを後から判定しにくい。長い出力は、作業記録や完了証跡の代わりにはならない。

## workflow protocol が行うこと

workflow protocol は、各 Skill 実行を次の順序で包む共通の制御である。

```text
依頼
  -> Skill の選択
  -> run: 実行記録と役割を作成
  -> 実行: 作業項目、成果物、根拠、未解決事項を記録
  -> verify: 記録上の作業漏れを決定論的に検査
  -> quality: 必要な場合に成果物の受入れを別途確認
  -> handoff: 次の担当者・次の作業へ渡す
  -> close: 完了、ブロック、またはエスカレーションを確定
```

実際には `xrefkit skill run` が run log と実行・確認・品質確認・引き継ぎの
役割を作成する。実行中には、具体的な作業項目、成果物と根拠、unknown / risk /
judgment を記録する。`xrefkit skill verify` はその記録を読み、未完了項目、
成果物の記録漏れ、未解決事項、役割や進行の不整合を検査する。

検査が通らなければ、作業は完了ではない。AI や人は不足を補い、再度検査するか、
解けない事項を明示して引き継ぐ。`xrefkit skill close` は、この状態を完了、
ブロック、またはエスカレーションとして残す。

### この仕組みが防ぐこと

| 起きやすい状態 | workflow protocol による扱い |
| --- | --- |
| AI が一部だけ実行して応答を終える | 未完了の work item が残るため、完了として close できない。 |
| 出力はあるが、確認根拠がない | 成果物と evidence の対応が記録されず、検査で不足として扱われる。 |
| 不明点を推測して進める | unknown / risk / judgment として記録し、解決または引き継ぎの対象にする。 |
| セッションが終わる、担当が替わる | run log に残った作業状態、根拠、未解決事項、handoff から再開できる。 |
| 実行した AI が自分で品質を承認する | workflow の検査と、必要な quality review を実行役と分離する。 |

これは、AI の中断を物理的になくす機能ではない。中断しても、未了の仕事を
成功扱いにせず、再開または引き継ぎに必要な状態を残す仕組みである。

## Skill が行うこと

Skill は、AI に任せる仕事の単位である。Skill は、何でもできる一般指示ではなく、
次のような責務のまとまりを定義する。

- どの目的の依頼に使うか。
- 何を入力として受け、どの判断を行うか。
- 何を成果物として返すか。
- どの知識を必要に応じて読むか。
- 何を扱わず、どの Skill または人へ引き継ぐか。

Skill の識別は `capability`、`tuning`、`responsibility` の三つで行う。
能力、対象に合わせた調整、業務上の責務を分けることで、似た依頼でも
適切な作業単位を選びやすくする。

たとえば、既存コードを変更する仕事は一つの巨大な「開発 Skill」にしない。
構造の把握、制約の導出、設計、実装、コードレビュー、テスト確認のように、
判断と成果物の境界が異なる単位へ分ける。それぞれの Skill は、自分の責務を
完了させ、次の責務へ必要な根拠と未解決事項を handoff する。

## なぜ責務を限定するのか

AI の能力が責務を限定するだけで普遍的に最大になる、という性能保証ではない。
しかし、責務が明確なほど、AI に渡すべき判断、入力、知識、出力、完了条件を
小さく定義できる。そのため、業務で必要な品質を出しやすく、確認もしやすくなる。

| 一つの大きな依頼 | 責務を限定した Skill |
| --- | --- |
| 調査、判断、実装、確認、報告が混在する | 一つの判断方法と成果物の境界を持つ |
| 必要な文脈が増え、不要な情報も混ざる | 必要な Knowledge だけを XID で選んで読み込む |
| 何が終われば完了か曖昧になりやすい | work item、成果物、確認、handoff を定義できる |
| 失敗時の原因が追いにくい | どの責務、根拠、判断、引き継ぎで止まったかを追える |
| 次の人や AI が作業を引き継ぎにくい | 入力と出力の契約を持って次の責務へ渡せる |

重要なのは、作業を機械的に細分化することではない。人または AI が一つの
判断方法と一つの成果物に責任を持てる境界で分けることである。細かすぎて
毎回統合が必要な分割も、依然として一つの Skill が複数の異なる判断を抱える
分割も、目的に合わない。

## Skill と workflow protocol の分担

| 要素 | 担当すること | 担当しないこと |
| --- | --- | --- |
| Skill | 業務固有の手順、判断方法、入出力、必要な Knowledge、Skill 固有の停止条件 | 全 Skill 共通の進行管理や、実行者自身による完了承認 |
| workflow protocol | 実行記録、役割分離、進行検査、closure、handoff の状態管理 | 業務の意味を理解して成果物の内容を自動採点すること |
| Knowledge | 判断に必要なドメイン規則、構造情報、根拠 | 実行の順序や完了状態の管理 |
| 人間 | 目標設定、必要な承認、例外判断、受入れ責任 | 会話履歴だけを頼りに作業状態を復元すること |

この分担により、Skill に共通の校正文言や一般的な作業漏れ対策を重複して
書かない。共通の進行と完了制御は workflow protocol に置き、Skill には
その業務でしか使わない判断方法と境界を置く。

## 説明するときの一分版

AI は途中で止まることがあります。問題は、止まったこと自体ではなく、
途中の状態が「完了」に見えてしまい、何が残ったか分からなくなることです。

XRefKit では、AI に任せる仕事を Skill として責務単位に定義します。さらに
workflow protocol が、作業項目、成果物、根拠、未解決事項、確認、引き継ぎを
記録し、必要な項目がそろうまで完了扱いにしません。

その結果、AI は限定された判断に集中でき、途中で止まっても次の AI や人が
同じ作業記録から再開できます。これは AI を止めないための仕組みではなく、
AI が止まっても仕事を失わず、未確認の仕事を完了扱いにしないための仕組みです。

## 8枚で説明する場合の構成

1. AI は出力できても、仕事が完了したとは限らない。
2. 中断、確認漏れ、未解決事項、引き継ぎ漏れが業務上の問題になる。
3. Skill は AI に任せる責務と判断の境界を定義する。
4. 責務を限定すると、必要な知識と成果物を絞り込める。
5. workflow protocol は各 Skill を記録、検査、handoff、closure で包む。
6. `verify` は作業の進行漏れを検査し、quality review は成果物の受入れを別に確認する。
7. 中断時は run log を基に再開または引き継ぎ、未完了を完了扱いにしない。
8. AI 活用を、単発の回答生成から継続可能で監査可能な業務実行へ変える。
