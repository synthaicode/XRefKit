# Shared Asset Update Gate

This contract governs the selected Skill/Knowledge governance entry. It is
loaded when preparing or analyzing that entry, not as a startup-wide rule corpus.
Its scope is explicitly integrated application endpoints; raw filesystem edits,
all Docs, other publication routes and runtime activation are not intercepted.

## Responsibilities and required evidence

The specialist owns content/meaning and its existing checks. QA checks agreed
requirements; humans choose corrective directions and adoption. The isolated
gate analyst checks common management evidence. The host owns real dispatch
and verifies execution provenance. The deterministic entry validates immutable
packet, receipt, scope and target identity. Application additionally requires
the existing trusted human authority mechanism. No actor's completion label
replaces another actor's authority.

Required common checks are `authority`, `candidate_identity`,
`external_references`, `specialist_evidence`, `handoff`. A packet includes this
rule source with its content identity; caller-selected extra rules cannot omit
these checks. Each obligation has an evidence-linked finding and rationale.
Missing or changed candidate, target baseline, rule, specialist evidence or
receipt cannot authorize application. Specialist refusal, applicable QA failure
and unresolved semantic conflicts remain refusals through this route.
Nonapplicability requires a supported reason and cannot waive mandatory identity,
scope or handoff. Structure validation does not establish semantic truth.

## External reference recording

Inspect actual candidate use, not only URL appearance. Record one or more uses
as `fixed_basis`, `current_information` or `navigation`. Fixed basis identifies
the source content used to create or judge the asset: source locator, use,
acquisition date, saved source and reproducible version/commit identifier.
Current information records purpose and the occasion/condition requiring current
information. Navigation is not an evidential dependency and does not require
universal version pinning. Already trusted sites are not reapproved merely
because a reference exists or was updated. This does not relax the ambient
external-input guard or treat a website domain as source truth.

Preserve the [source storage contract](../../reference/020_sources.md#xid-2FAD591BF725).
GitHub commit links alone do not replace required originals/Web snapshots.
Only its existing xddp exception permits external-only source recording; an
exception row must identify evidence establishing that applicability. This
contract does not create a general external-only exception. Source-use material
and stored-source/exception evidence belong to the frozen packet where used.

The gate result explicitly records `external_reference_disposition`:
`no_external_refs` means the candidate was inspected and no applicable external
use found; `classified` requires nonempty role records. Each role record has
`role`, `source_locator`, `used_for`, `acquired_at`, `stored_source`,
`fixed_identifier`, `refresh_condition`, `source_exception`,
`exception_evidence`. Irrelevant values are explicit nulls. `source_exception`
is null or `xddp`; nonnull exception requires frozen evidence. Fixed basis
requires acquisition date and reproducible identifier, and the required saved
source unless the existing explicit exception applies. Current-information use
requires a refresh condition; navigation records its use without invented
continuous monitoring. One source may legitimately have multiple role records.

## Execution and reflection boundary

An actual isolated child Skill run corresponds to the originating parent/root/
workitem and completes under the operating contract. Its saved result body
excludes its own output pointer. The trusted host binds packet, execution,
child-log and result identities and adds the output hash. A plan, caller boolean,
unsigned caller receipt or parent-produced analysis is not actual isolated
execution evidence. Missing trusted host integration is an explicit limitation.

The selected endpoint validates the receipt immediately before application,
verifies separate human approval, checks expected target hash/absence and
records actual reflection evidence. A post-check candidate change requires
rechecking. Common checks do not adopt a Skill, promote maturity, activate a
runtime or authorize bulk companion-file updates. Cooperating endpoint locks
do not prove protection against arbitrary filesystem writers.

Corrections analyzed by a retrospective remain work evidence until explicit
human adoption enters an eligible update route. Retrospective consent alone
never grants application. Source-role fields and obligation results are this
entry's records, not new Workflow/Human Evaluation status meanings.
