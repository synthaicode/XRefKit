# Skill Meta: db_design

- skill_id: `db_design`
- summary: produce implementation-ready brownfield database design artifacts from approved planning inputs and current source-structure findings
- use_when: a design task changes database schema, persistence behavior, ORM mapping, migrations, data correction, query/write paths, or data ownership and needs an implementation-ready DB design package before coding
- input: approved requirements, work plan, source modification policy, data change policy, current source-structure finding XIDs, current database state analysis report or XID with DB-unit SQL export basis, database-related source evidence, existing DDL/schema/migrations/ORM mappings, and optional constraint-derivation outputs
- output: database design package with logical and physical model changes, DB-unit SQL export basis reference, DB naming rule basis and candidate names, table-definition local rule basis for column names/types/lengths/precision/scale/nullability/defaults/identity/computed/collation/concurrency fields, stored procedure naming rule basis, stored procedure granularity basis, stored procedure return/result convention basis, transaction configuration, isolation level, transaction granularity basis, SQL writing rule basis, SQL error-handling rule basis, DDL/query construction rule basis for `DROP`, existence checks, idempotency, and script style, migration and data correction plan, read/write path impact, compatibility and rollout notes, transaction/concurrency behavior, validation checks, source-analysis basis XIDs, current database state basis reference, required derivation outputs, and unresolved assumptions
- maturity: `draft`
- execution_mode: `local_default`
- capability_layering: `required`
- workflow_protocol: `required`
- capability: database design
- tuning: brownfield database design before implementation
- responsibility: create implementation-ready database design while keeping requirement confirmations, source-structure evidence, and migration risks explicit
- os_contract: v1
- constraints: do not implement migrations or code changes; do not invent schema behavior from ORM or DDL alone; use registered source-structure finding XIDs and current database state analysis as the source-analysis basis; require DB-unit SQL export basis from current database state analysis or an explicit missing-impact note; route missing or stale current database state through `db_current_state_analysis`; use current database state DB naming rule analysis for table, column, constraint, index, migration, entity, DbSet, raw SQL, job, message, and configuration naming; use stored procedure naming rules before proposing stored procedure names; use table-definition local rules before proposing column names, types, lengths, precision, scale, nullability, defaults, identities, computed columns, collation, or concurrency columns; use database-level local rules for stored procedure granularity, transaction configuration method, isolation level, SQL writing style, SQL error-handling style, and DDL/query construction rules such as `DROP` usage and object-existence checks; use stored procedure analysis before choosing `OUTPUT`, result set, return code, status/message output, side-effect-only, error-based, or mixed return/result patterns; use transaction-granularity and isolation-level evidence before choosing caller-controlled, whole-procedure, operation-block, per-row/per-item, per-batch/chunk, nested, ambient, job-level, migration/deployment, or external framework transaction boundaries; use SQL error-handling evidence before choosing `TRY/CATCH`, `@@ERROR`, `THROW`, `RAISERROR`, return-code based, output-status/message based, or no explicit error handling; use Brownfield API Naming Extractor when names cross external or data-flow boundaries; route unresolved DDL/schema/operation behavior to constraint derivation before implementation-facing closure; keep data migration, data correction, compatibility, transaction, and rollback assumptions explicit
- lifecycle:
  - startup: confirm approved planning/design inputs, database scope, data change policy, current source-structure finding XIDs, current database state analysis, existing schema/migration/ORM evidence, and whether required naming/persistence evidence exists in canonical knowledge
  - planning: classify DB design areas, identify whether current database state analysis is missing or stale, identify logical and physical model deltas, identify data migration and correction needs, select DB naming rule evidence, stored procedure naming rules, table-definition local rules, database-level local rules, stored procedure return/result convention basis, transaction-granularity basis, isolation-level basis, and SQL error-handling rule basis, decide required constraint-derivation routes, and define design output rows
  - execution: draft the database design package from current database state analysis and registered structure/naming evidence, apply DB naming rule analysis to candidate names, apply stored procedure naming rules to stored procedure names, apply table-definition local rules to column definitions, apply database-level local rules to stored procedure granularity, transaction configuration, isolation level, SQL writing style, SQL error-handling style, and DDL/query construction rules, apply stored procedure analysis to return/result convention and transaction granularity, specify migration and correction sequencing, record read/write path impacts, and incorporate confirmed constraint-derivation outputs
  - monitoring_and_control: downgrade unsupported schema behavior, missing current-state evidence, missing naming-rule analysis, missing stored procedure naming rules, missing table-definition local rules, missing database-level local rules, missing stored procedure return/result convention basis, missing transaction-granularity basis, missing isolation-level basis, missing SQL error-handling rule basis, missing DDL/query construction rules, naming choices, column-definition assumptions, stored procedure assumptions, SQL writing assumptions, migration assumptions, compatibility claims, and transaction assumptions to `unknown`; stop before closure if required DB current-state, source-structure, or derivation evidence is missing
  - closure: hand off the DB design package with source-analysis XIDs, naming evidence, migration/correction plan, validation checks, unresolved items, and required downstream implementation/test/release notes
