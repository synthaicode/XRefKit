### Revised responsibility boundary for dispatch, projection and recovery

**Proposed decision revision R2.** Applies to the optional API execution path described in #199 and to the offline contract examples in #200. Gateway's single ready item per call and one active item per returned state do not by themselves serialize multiple callers using the same state. Preserve `dispatch_owner=client_host`, existing host/CLI/MCP paths, existing result enums, human authority and independent quality criteria. The Runtime owns assignment, reroute and result projection authority; the selected client host coordinates admission; the lower Controller executes only its current admitted assignment.

| Boundary | Proposed rule and responsibility |
| --- | --- |
| One execution owner per active assignment | The upper Runtime/host integration admits a single executor in an authoritative durable claim shared by all contenders for the same work item. Key by the stable Runtime work-item identity in its flow, with the active assignment/route revision, generated binding identity, selected backend and monotonic owner generation as bound fields. Atomically compare the current Runtime state and claim it before exposure to effect-capable execution. A duplicate dispatch delivery reuses the existing claim/receipt without starting another executor; an incompatible or concurrent claim holds. A later assignment for the same work item is possible only through upper-layer replacement under the rules below. If claim storage, freshness comparison, or a common authority for all contenders is unavailable, the API backend holds. |
| Last check and dispatch admission | Before **every** actual API send or Tool invocation, the Controller asks the host/runner effect gate to verify the current generated and validated ExecutionBinding (legacy marker-free input is insufficient for this API path), latest assignment/route/binding, owner generation, exact operation/target, #203/#204 policy/permit and reservation, cancellation/deadline and #207 journal state. As the final step before handing off to transport, atomically consume a one-use dispatch admission and persist the exact intent/attempt with the claim generation. Serialize this transition with revocation and assignment replacement. A stale/consumed admission or obsolete runner cannot start another effect. If the handoff boundary cannot enforce that rule, do not dispatch. Once admission has crossed that boundary, treat an interrupted or unrecorded send as possibly submitted; expiry or a local cancel does not prove the sender never acted. |
| Result and model conformance | One authorized upper projection path validates assignment/route/binding, claim generation, result/attempt correlation, and selected versus actually observed model **before** invoking the existing Gateway recorder with a success. On mismatch or missing observed identity, preserve the exact observation and safe references as held evidence for Runtime review; do not submit a success, invent a model or extend an enum. If projection receipt is unknown, reconcile before re-projecting. Identical receipts are idempotent; stale or conflicting receipts may reconcile their attempt/usage when proven, but cannot advance the current assignment. Verify/close and human acceptance remain separate. |
| Unknown outcome and reconciliation | A timeout, disconnect, crash, cancellation after possible send, or missing/contradictory receipt creates a hold for that logical operation. Keep the original intent, IDs, evidence and #203 reservation, distinguishing effect seen, usage known and result known. #207 reconciles with a correlated authoritative receipt or separately authorized read-only postcondition/status on the original scope. Reuse a recovered result without invoking the operation again. Confirmed no-submit/no-effect can clear the effect hold as permitted by policy; absence of a response, lease expiry and aggregate billing are insufficient. An unresolved attempt is handed off without replay or replacement. A late receipt updates its own attempt and ledger idempotently. |
| Same-assignment retry or upper-layer replacement | The Controller may propose another bounded attempt only within its current assignment, backend/model and scope, after the effect hold is resolved with verified no-submit/no-effect or a specifically approved exact-operation replay contract protects against duplicate effects. For approved replay, preserve the logical operation identity and required original idempotency key; use a new attempt identity and applicable budget reservation. Unknown usage remains reserved/accounted under #203. Correlation IDs alone do not prove replay safety, and an unresolved paid provider send stays held until sufficient provider evidence permits a next action under #203/#207. Require current authority, no cancellation, remaining deadline/budget, and a new last-check admission. When these conditions fail or a backend/model/scope/runner change is needed, hand back to the upper Runtime. Only the Runtime can retire the previous claim and grant a new route/assignment after revoking old admissions, proving the old executor cannot initiate any new effect, and resolving outstanding effect/delivery ambiguity. An expired claim, missing receipt, or retry exhaustion alone never enables takeover. |

#### Mandatory duplicate prevention at the actual effect boundary

The requester requires duplicate prevention on the actual provider-send and Tool-invocation paths. R2-A's exclusive assignment and durable admission are prerequisites. The receiving boundary must show that a stale, revoked or duplicate executor cannot cause an additional outbound request or Tool invocation, including when a process resumes after pausing between admission and send. The effect gate must control the actual initiation of the request or invocation. A separate permit check/consumption followed by an independently resumable sender is insufficient. Where a sender already passed the admission point, prove it has been stopped or drained and resolve its effect before granting a replacement. Every actual request or Tool operation, including an adapter retry or redirect that starts another request, must pass the applicable gate; deny bypass paths. If the old sender cannot be fenced or already-admitted work remains uncertain, stop new dispatch or replacement and reconcile via #207. Late evidence can update the original attempt only.

**Acceptance requirement.** #202 and #204 verify their actual provider transport and effect-capable runner against an instrumented local receiver or executable fixture under separately approved verification scope. Exercise concurrent duplicate delivery, paused sender versus revocation/replacement, restart and transport retry/redirect. Require that unadmitted, stale and duplicate attempts cause zero additional requests at the receiver or invocations at the runner. Compare receiver counts and operation/attempt evidence. Counters in #200's stub-only contract examples do not supply this implementation proof. #206/#207/#208 verify cross-component handoff and preserve the unknown state; #210 integrates the evidence. This requirement covers requests emitted through the controlled path. Provider-side replay remains governed by the verified #203/#207 contract and original attempt evidence.
